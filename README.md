# hackchild-architecture

How the hackchild stack actually works across `hackchild-mobile` and
`hackchild-backend` — written once, kept honest automatically.

Each document traces one behaviour end to end and records the exact source files
it was written from. A nightly job re-checks those files and stamps every
document with whether it still matches the code.

> **Assistants: do not read this file.** It is for people. Grep
> `index/manifest.tsv` instead — one line per document, so a lookup costs the
> same whether the repository holds three documents or three thousand.
>
> ```sh
> grep -i 'optimistic update' index/manifest.tsv
> ```

---

## What belongs here

| Write a document when | Don't bother when |
|---|---|
| You had to open **both repositories** to answer the question | The whole answer lives in one repo, in a straight line |
| The trail went cold at a seam — an event bus, a webhook, a feature flag | An assistant gets it right by reading one file on demand |
| An incident taught you something the code does not say | It's a rename, a config value, or already obvious |

Documents are filed by **domain** — the part of the product they describe.
Whether a document is a `flow` (a behaviour crossing both repos) or a
`mechanism` (one subsystem) is recorded in its frontmatter, not in its folder,
so a document never has to move when its scope changes.

## Status — read it before trusting a document

Every document lists the source files it was written from, plus the **git blob
SHA** of each at the moment of writing. A nightly job asks GitHub for the
current SHA of every file in each code repo — one request per repo, regardless
of document count — and compares.

| Status | What it means | What to do |
|---|---|---|
| `verified` | Fingerprints match the code | Trust it |
| `stale` | The code has changed since this was written | Read it, but check any load-bearing claim |
| `needs-review` | Fingerprints were refreshed, but **nobody has read the prose** against the change | Treat exactly as `stale` |
| `observed` | Written from one side of the stack only | Trust it about that side; the other is inference |

A stale document is not necessarily wrong. It just has not been checked since
the code moved, and it says so rather than pretending otherwise.

**When a document and the code disagree, the code wins.**

## Tools

```sh
node tools/check-fingerprints.mjs --remote --owner adamdahan   # against GitHub
node tools/check-fingerprints.mjs --local ../                  # against local clones
node tools/build-index.mjs                                     # regenerate the indexes
```

`build-index.mjs` writes three derived things — `index/manifest.tsv`,
`index/watchers.json`, and the document table above. **None of them are ever
hand-edited.** `watchers.json` inverts the relationship: source file → the
documents that cite it, which is what lets a pull request tell you which
documents it is about to age.

## Adding a document

1. Put it in `docs/<domain>/<slug>.md`
2. Add frontmatter — `kind`, `domain`, `keywords`, `status`, `vantage`,
   `verified_on`, `verified_by`, `sources`
3. List **5 to 15 specific source files.** Never a directory, never a glob.
   This is the single most important rule here: watch too much and every
   unrelated commit flags the document, people learn to ignore the flags, and
   the system quietly stops working.
4. Fill each source's `blob` with `git hash-object <file>` run in that repo
5. Write a **Gotchas** section
6. Run `node tools/build-index.mjs` — the table above updates itself

The Gotchas section is the part that never expires, because it was never
derivable from the code in the first place. Flow steps, schemas and signatures
go stale; the reason something is the way it is does not.

## How it reaches developers

Every merge to `main` mirrors the documents, the lookup skill, and
`.github/copilot-instructions.md` into both code repositories. Nobody clones
this repo, and nothing needs installing — a developer who has only ever cloned
`hackchild-mobile` still gets answers about the backend.

Those mirrored copies are **generated and read-only**. Corrections belong here,
where the fingerprint and review machinery lives; a pull request that edits them
in a code repo fails with a pointer back to this repository.
